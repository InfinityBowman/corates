- **`packages/web/public/_headers`** - Cache-Control rules and security headers (CSP, X-Frame-Options, Referrer-Policy, Permissions-Policy) applied to static responses. Update this when adding a new external domain (CSP `connect-src` / `script-src` / `img-src` / `font-src` / `style-src`), introducing a new asset type with custom cache requirements, or relaxing/tightening any security header. Test changes locally with `pnpm --filter web build && pnpm --filter web preview` before deploying.
- **`packages/web/public/_redirects`** - 301 redirects for trailing-slash canonicalization on public routes. **When you add a crawlable public route (marketing, legal, auth, resources, or the local appraisal entry point), add a `/route/ /route 301` entry here.** Cloudflare Workers Static Assets emits a 307 (temporary) for trailing-slash variants by default, which causes search engines to repeatedly probe the slashed form and report it under "Page with redirect" in Google Search Console. The 301 rules in `_redirects` override that behavior so the slashed variant is permanently canonicalized. Entries are kept alphabetical; routes disallowed in `robots.txt` are omitted, since crawlers never request them.
- **`packages/web/public/robots.txt`** - Crawl directives plus the sitemap reference. Everything is allowed by default; the `Disallow` entries cover API endpoints and health probes, authenticated app surfaces (`/admin`, `/dashboard`, `/settings`, `/orgs/`, `/projects/`), and token-bearing or transactional pages (`/invite/`, `/verify-email`, `/complete-profile`, `/reset-password`). `/signin` and `/signup` stay crawlable. **When you add a route under an authenticated or transactional prefix that is not already covered, add a `Disallow` entry.** Note that `Disallow` only stops crawling; it is not a substitute for a `noindex` robots meta tag on a page that must never appear in results.

  Cloudflare **prepends** its own managed block to this file at the edge rather than replacing it: the Content Signals Policy preamble and the AI-crawler `Disallow` rules (Amazonbot, Bytespider, CCBot, ClaudeBot, GPTBot, Google-Extended, meta-externalagent, ...) are emitted between `# BEGIN Cloudflare Managed content` and `# END Cloudflare Managed Content`, and the contents of this file are appended verbatim after that. Verify with `curl -sS https://corates.org/robots.txt`. Two consequences: the served file contains **two `User-agent: *` groups** (Cloudflare's carries only `Content-Signal`, ours carries the `Allow`/`Disallow` rules) which conforming parsers merge per RFC 9309; and the AI-bot policy is owned by the Cloudflare dashboard, not this repo, so do not duplicate those directives here or the two will drift.

- **`/sitemap.xml`** - Served by the `sitemap[.]xml.ts` server route from `packages/web/src/lib/sitemap.ts`, not from a static file. Resource pages come from the registry in `src/lib/resource-pages.ts`, and their `lastmod` is the `dateModified` field on the page's content record (`tool-content.ts`, `comparison-content.ts`); the `/resources` index takes the latest of those. Marketing and legal pages are listed by hand in `STATIC_PAGES` in `sitemap.ts`. **When you add a public marketing or legal route, add it to `STATIC_PAGES`; when you add a resources page, add its content record to the registry. Bump `dateModified` (or the static `lastmod`) on any page whose content or meta you changed.** Only include URLs that return 200, self-canonicalize, and are not disallowed in `robots.txt`; app and auth routes are deliberately excluded.

The three static files above are copied verbatim from `public/` to the build output by Vite. The build log will show `Parsed N valid redirect rules` and `Parsed N valid header rules` to confirm `_redirects` and `_headers` were picked up.

Per-route metadata (title, description, canonical, Open Graph, Twitter) lives in each route's `head: () => ({ meta, links })` block. Routes without their own `head` inherit the site defaults from `packages/web/src/routes/__root.tsx`, which also carries the site-wide JSON-LD `@graph` (Organization, WebSite, WebApplication). Those three entities have stable `@id`s exported from `src/lib/structured-data.ts`. Each `/resources` page emits its own `@graph` from `head()` via the helpers in `src/lib/resource-head.ts`: a `TechArticle` (author and publisher referencing the Organization, `isPartOf` the WebSite) whose `mainEntityOfPage` is the page's `WebPage` node, which carries the `BreadcrumbList` and, when the page has one, the FAQ (the page is typed `WebPage` and `FAQPage` together). The index emits a `CollectionPage` with an `ItemList`. `datePublished` and `dateModified` on every article come from the same content fields the sitemap reads. The server stops running `head()` at the first `ssr: false` match, so a `head` on a route nested under `_app` or `_auth` never reaches the served HTML; crawler-facing meta for those trees (the `noindex`) lives on the layout route itself. Both trees are noindexed wholesale - they render from IndexedDB and per-user state, so a crawler only ever receives an empty shell. The server-rendered `/resources/*` guides are the indexable surface for appraisal-tool queries and link into `/checklist` as their call to action. Note that `/checklist` is still _crawlable_ in `robots.txt` and must stay that way: a `Disallow` would prevent crawlers from ever fetching the page to see the `noindex`. Structured data must only assert what is verifiably true of the product - no ratings, review counts, or credentials that are not backed by the page or the repo.
